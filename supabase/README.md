# The desk's database: apply by hand

The dispatch desk needs **its own Postgres / Supabase project**. Do not use the phone app's `truelane-prod`: it already has tables called `loads`, `drivers` and `vehicles` with a different model (`user_id`, `fleet_id`, epoch-millisecond columns), and the desk's first migration would fail on them or corrupt them. The phone's own folder, `TRUELANE/supabase`, is not used for the desk either.

Prisma (`prisma/migrations`) is the source of truth. Everything in this folder is generated from it by `npm run db:export-supabase` (from `dispatch-desk`) and a test fails if the two drift. Do not edit these files; change the Prisma migration and regenerate.

## What is here

| File | What it is |
|---|---|
| `migrations/20261027000000_extensions.sql` | Preflight: `pg_trgm` (the search indexes need it). |
| `migrations/20261028000000_…` to `…20261128000000_telematics_radar.sql` | The desk's 38 migrations, in order, verbatim from Prisma. |
| `migrations/20261129000000_enable_rls.sql` | Row level security on for every table, no policies (see below). |
| `apply-all.sql` | All of the above in one file, for one paste into the SQL editor. |
| `verify.sql` | Checks the result by the objects themselves. |
| `lockdown_rls.sql` | The RLS statement alone, to re-run after any later migration. |
| `mark-applied.sh` / `.ps1` | Tells Prisma its history is already in (see below). |

**Left out on purpose:** `20261028010000_retire_legacy_dispatch_tables`. It drops 24 old tables and 28 types that a fresh database never had, so on a new project it fails with "relation does not exist". It is for a database that still has the retired backhaul app's tables. The 35 older Prisma folders (`2026-04` to `2026-08`) are that retired app and are not part of the desk.

## Apply it (pick one)

1. **SQL editor, one paste (simplest).** Open the desk project's SQL editor, paste all of `apply-all.sql`, run. The editor runs it as one transaction: if anything fails nothing is half-applied; fix and run again.
2. **SQL editor, a file at a time.** Run the files in `migrations/` in filename order.
3. **Supabase CLI.** From `dispatch-desk`: `supabase db push --db-url "<direct connection string, port 5432>"`.

Then run `verify.sql`: every row of the first result should say `present`, the second result (tables with row security off) should be empty.

## Row level security

Supabase publishes every table in `public` through its REST API. With row security off, anyone holding the project's anon key could read loads, driver pay and customer rates. The last file turns it on for every table with **no policies**, which closes that door. The desk's own server connects through Prisma as the owning `postgres` role, which is not subject to it, so the desk is unaffected. New tables start with it off: run `lockdown_rls.sql` again after applying any later migration.

## Keep Prisma in step

Applying by hand leaves Prisma's own history table empty. If the desk will ever run `prisma migrate deploy` against this database, run `mark-applied.sh` (or `mark-applied.ps1` on Windows) once, from `dispatch-desk`, with `DATABASE_URL` set to the new database's **direct** connection. It records all 39 desk migrations as applied, including the retire one that was never run.

## Notes

- Use the **direct** connection (port 5432) for Prisma migrate commands, not the pooled (pgbouncer) one.
- Ids are `text` generated by Prisma (cuid), not uuids. A row inserted by hand needs an id.
- `pg_trgm` is created in `public`. If you ever see `operator class "gin_trgm_ops" does not exist`, run `create extension if not exists pg_trgm with schema public;` and apply again.
- Do not paste any of this into `truelane-prod`.
